# Feature Specification: Privacy-safe Azure Blob product telemetry

## Current T009 consent-peer correction

Owner decision `compact-four-doc-peer-repair` (`01a148a6-1a13-7855-b104-f267c9b8cf5b`) adds only committed-state convergence in the existing `ProductTelemetrySettingsViewModel` and its Package tests; frozen product head `02e5e76532deaf21600b88b7318ad3c60034314d` and every prior behavior, privacy, lifecycle, and evidence obligation remain unchanged.

After an opt-in or opt-out callback completes, the origin model rereads its own persisted consent; only its latest matching intent may publish committed display and emit a value-free completion pulse. Loaded peers keep their previous committed value while persistence is pending, respond only by rereading their own preference object, reject stale load/refresh results during rapid choices, and perform no consent write, identity request, activation, admission, or upload. A model over another store retains that store's value. The existing process-local notification/completion boundary is trusted and adds no value-bearing payload, authority, manager, executor, state machine, protocol, dependency, singleton, App test seam, event type, gate, permission, transport, or iPad multi-window scope.

Deterministic no-sleep Presentation tests separately gate same-store opt-in and opt-out, prove pending display stability then committed reread convergence, cover rapid-choice/overlapping-refresh stale rejection, assert one origin callback with zero peer side effects, and prove different-store isolation. This is `US1/AC9`, `FR-027`, and `SC-009`; all later references use those identifiers.

## User Scenarios & Testing

### User Story 1 - Observe a real TestFlight product event (Priority: P1)

As the product owner, I can explicitly enable “Send usage data”, use a configured macOS TestFlight build once, and find a privacy-approved product event in the existing telemetry container, so consented product usage is observable without creating another cloud resource.

**Why this priority**: The workflow outcome is one real product event delivered from VoxPocket; local or synthetic evidence alone does not complete it.

**Independent Test**: A credential-free receiver fixture proves the two product event shapes and flush lifecycle before merge; after the Owner supplies credentials and explicitly authorizes the existing release workflow, the tester separately opts in through Settings and performs an approved action, then the Team Lead records the TestFlight build number and one read-only blob listing result.

**Acceptance Scenarios**:

1. **US1/AC1** — **Given** a macOS TestFlight build has valid approved Blob configuration and the user has separately enabled “Send usage data”, **when** a later app startup completes or the user performs an approved key action, **then** the matching product event is admitted and a lifecycle flush attempts delivery to the configured existing container.
2. **US1/AC2** — **Given** product telemetry is enabled, **when** events are recorded, **then** the only product event types are `product.user_action` and `product.performance`, with closed action/operation labels and finite numeric duration values only.
3. **US1/AC3** — **Given** the shared adapter emits its owned operational heartbeat, **when** product-event inventory is assessed, **then** that documented content-free heartbeat is treated as adapter diagnostics rather than a third product event type.
4. **US1/AC4** — **Given** an accepted product event is pending, **when** startup completes, a recording/session ends, or the app resigns active, **then** a non-blocking flush is requested; failure or cancellation causes no host/manual deletion, and pending files not already evicted by the accepted capacity policy remain available for retry.
5. **US1/AC5** — **Given** the reviewed change is merged, the Owner has added both secrets, and the Owner explicitly authorizes the existing macOS release workflow, **when** the tester separately opts in through “Send usage data” and uses that TestFlight build for an approved action, **then** the Team Lead can record the build number and blob name using a read-only listing without recording payload or credential contents.
6. **US1/AC6** — **Given** the standard bundle initializer is used, **when** the host constructs the service, admits a product event through `track`, or requests `flush`, **then** those host calls run only through one serialized non-`@MainActor` lifecycle coordinator and no UI/lifecycle caller is synchronously blocked by file I/O; only the SDK-owned, internally synchronized, content-free startup/daily heartbeat is exempt from traversing the host coordinator.
7. **US1/AC7** — **Given** a new or existing installation has not explicitly enabled “Send usage data”, **when** VoxPocket starts, **then** the persisted setting defaults off and no Blob service is constructed, event is admitted, or upload is attempted; turning it off later immediately stops new admission and upload without host/manual deletion, retains non-evicted pending local files plus any previously created install UUID, and a later explicit opt-in reuses that same UUID.
8. **US1/AC8** — **Given** no install identity exists, **when** the user opts in for the first time, **then** VoxPocket persists consent without creating identity until an eligible interactive-app composition has valid Blob configuration; that eligible branch creates and persists one random non-personal install UUID, and later eligible launches and explicit opt-ins reuse it for the app installation's lifetime. Missing/invalid configuration and excluded hosts create no identity, consent-off state never actively requests or uses one, and no Settings Reset or identity-rotation surface exists in v1.

### Edge Cases

- Only one of the two Blob settings is present, or a setting still contains `$(...)`.
- The endpoint is non-HTTPS; the SAS is a user-delegation token, contains an unsupported query name, has `sr` other than `c`, or has an explicit `sp` other than `c`; the stored-policy token lacks `si`/`sig`; metadata is not allowlisted; or the store is already leased by another instance.
- An event has a safe name but an unknown key, unsafe label, non-finite duration, or sensitive sentinel embedded in an otherwise plausible field.
- The app is terminated or disabled during a flush; the host may not erase an unconfirmed file, provider-owned capacity eviction remains allowed, and no next request may start on the cancelled generation.
- Consent is disabled while admission or upload is active; the coordinator stops the active generation, admits no later event, retains non-evicted unconfirmed files without host/manual deletion, and does not resume until a later explicit opt-in.
- A first opt-in races with repeated Settings toggle actions or eligible launches; consent-only writes create no identity, the first eligible interactive-app composition persists exactly one random UUID for the app installation's lifetime, consent-off work admits or uploads nothing, and later explicit opt-in reuses that same UUID.
- Several UI/lifecycle signals arrive while admission or flush is active; the host coordinator preserves admission order, joins rather than duplicates the active flush, and performs no synchronous file I/O on `@MainActor`. SDK-owned heartbeat ticks remain internally synchronized and off-main without becoming a host/product event bypass.
- Legacy Loki events originate concurrently from app-shell, Presentation, Application, and Infrastructure callers, including `@MainActor`; all requests enter the same serialized non-main coordinator, and flush drains prior admission rather than racing it.
- The `v0.2.0` tag is missing, moved, no longer annotated, or no longer peels to the reviewed commit; the atomic exact-`0.2.0`/off-main slice blocks and escalates instead of falling back to a revision selector.
- A Release build is produced without real secrets for CI proof; it must use synthetic values and never contact Azure.
- The Owner has not added secrets or has not explicitly authorized a TestFlight run; implementation may be merged, but production delivery evidence remains pending.
- A rollback encounters a pending capacity eviction or loss tombstone; producers stop, the `0.2.0` capacity-aware reader finishes paired cleanup after storage is writable, and only then may a separately reviewed older reader start. Already evicted batches are unrecoverable, and an older reader must not replay logically dropped files.

## Requirements

### Functional Requirements

- **FR-001**: VoxPocket MUST use SwiftPM `exact: "0.2.0"` for shared-telemetry across every Swift consumer manifest, dependency guard, current authority, and current projection. A branch, revision selector, or revision fallback is forbidden; the annotated tag object and its peeled commit are integrity evidence only. The protected constitution change MUST be a deliberate amendment naming the rule, reason, and migration impact and MUST record the Owner-approved `loki02v1` one-time deviation from repository-contract change-kind separation; `AGENTS.md` Red lines MUST contain only a pointer to that protected exception record, replacing its current “Approved exceptions: none” statement without authorizing any broader exception. Historical baseline evidence remains explicitly historical.
- **FR-002**: The existing Loki event service and local Loki log sink MUST remain separate from the Blob service; legacy events MUST NOT be fanned out to Blob implicitly.
- **FR-003**: The Blob service MUST use one dedicated Blob-only application-support store with one live owner and MUST NOT reuse, migrate, or delete Loki queue/log files.
- **FR-004**: Trusted app, build, and version metadata MUST be allowlisted from the built application; install identity MUST be a non-personal UUID created only by the first eligible interactive-app composition after explicit opt-in, persisted locally, and reused for the app installation's lifetime.
- **FR-005**: The product event vocabulary MUST contain exactly `product.user_action` and `product.performance`; allowed keys and closed labels are defined in the telemetry contract, and no generic free-text property is allowed.
- **FR-006**: The SDK-owned `telemetry.heartbeat` MAY carry only its documented content-free operational fields and MUST NOT be emitted by product callers. Decision 2A exempts only the initializer-owned, internally synchronized, off-main startup/daily heartbeat from the host coordinator; it does not permit a second host/store owner, a product `track` bypass, or main-thread synchronous persistence.
- **FR-007**: Blob admission MUST reject an entire event before accepted memory/storage/network state when its name, key, label, number, timestamp, or provenance violates the allowlist.
- **FR-008**: Audio, live/final transcripts, refined text, prompts, arbitrary error descriptions, credentials, endpoints, SAS values, and other user-derived text MUST never enter either Blob or Loki telemetry payloads.
- **FR-009**: Existing arbitrary error-description/reason telemetry fields MUST be replaced with closed content-free categories or removed, with sentinel regressions for the affected application and infrastructure boundaries.
- **FR-010**: Missing, empty, or unexpanded Blob configuration MUST use the adapter's disabled default without crash, identity provisioning, store access, enqueue, or network activity.
- **FR-011**: Present but invalid Blob configuration MUST fail only the Blob path closed, with fixed content-free diagnostics and no fallback receiver.
- **FR-012**: The interactive app MUST have at most one live Blob service/coordinator generation while consent is on and request non-blocking flushes after startup telemetry, at recording/session end, and when macOS resigns active; disabling, failure, or cancellation MUST cause no host/manual deletion, and non-evicted work remains retryable.
- **FR-013**: The source plist MUST contain `LokiKitBlobEndpoint = $(TELEMETRY_BLOB_ENDPOINT)` and `LokiKitBlobSAS = $(TELEMETRY_BLOB_SAS)`, and both build settings MUST be required for an enabled Release transport.
- **FR-014**: Real Blob endpoint and SAS values MUST come only from GitHub Actions secrets during the authorized macOS TestFlight archive. CI MUST write them to one untracked runner-temp xcconfig with mode `0600`, pass only its path via `-xcconfig`, and delete it in an `always`/`ensure` path; values MUST NOT appear in source, attachments, xcargs, command-line environment assignments, printable arguments, or logs.
- **FR-015**: Credential-free tests MUST cover disabled-without-configuration, exact privacy allowlists, the two product event shapes, SDK-owned heartbeat ownership, coordinator-only Blob construction/product `track`/lifecycle `flush`, serialized non-main legacy Loki `track`/`flush`, the actual exact-`0.2.0` adapter enqueue-return-before-flush barrier, adjacent-only flush coalescing plus the intervening-admission follow-up case, stored-policy SAS query compatibility, no transcription/refined/audio/error/credential sentinel persistence or transport, and flush lifecycle. Direct instrumentation tests are supplemental: rapid-release and startup/recording/session/resign-active flush regressions MUST also drive the real `AppDelegate` / `ServiceContainer` production boundaries so removing or reordering those callers fails the tests.
- **FR-016**: A required CI path MUST build a Release app with synthetic settings and inspect the processed plist for exact expansion; TestFlight packaging tests MUST prove both raw and shell/percent-escaped synthetic sentinel forms are absent from Release-path logs. Neither path may sign, upload, contact a live telemetry receiver, or expose a value-bearing argument.
- **FR-017**: Existing Debug/local development, macOS manual TestFlight trigger semantics, iOS development builds, iOS TestFlight disablement, signing, build numbering, upload, and release-tag behavior MUST remain compatible.
- **FR-018**: The TestFlight-injection PR body MUST list the exact Owner-only Decision 1A commands: create a stored access policy with key-based auth, permission `c`, and explicit UTC expiry; generate an HTTPS-only container service SAS with `--policy-name` and key-based auth; and set both GitHub Actions secrets. Committed artifacts MUST use placeholders instead of real cloud identifiers. The stored-policy token MUST use only supported query names with `sr=c`, non-empty `si`/`sig`, optional `sv`, and `spr=https`; policy authorization means explicit `sp` is normally absent, while any explicit `sp` MUST equal `c`. User-delegation fields and `--as-user` are forbidden, and agents MUST NOT execute, inspect, or persist the real token.
- **FR-019**: No existing test, assertion, privacy gate, release guard, or policy may be removed, skipped, or weakened to deliver this feature.
- **FR-020**: After merge, Owner secret provisioning, explicit release authorization, and a separate tester opt-in through “Send usage data”, one approved action in the TestFlight build MUST produce a blob that the Team Lead verifies read-only by recording the build number and blob name only. Owner release authorization MUST NOT be treated as end-user consent.
- **FR-021**: The `AzureBlobTelemetryService` bundle construction, with the provider-default `maxDiskBytes` argument omitted, plus every host product `track` and lifecycle `flush` call MUST execute through the same serialized non-`@MainActor` app-lifetime coordinator used for legacy Loki; `@MainActor` callers MAY only schedule asynchronous work. Decision 2A exempts only SDK-owned, internally synchronized, off-main heartbeat work performed after that construction.
- **FR-022**: Settings MUST expose a persisted `UserDefaults` opt-in named “Send usage data” that defaults off. The Settings write MUST persist only the consent Boolean and MUST NOT read, request, create, or return an install identity. Turning it off MUST immediately stop Blob admission and upload without host/manual deletion and retain non-evicted pending local files under SDK disable semantics; re-enablement MUST require a fresh explicit opt-in before either resumes.
- **FR-023**: After explicit opt-in is persisted, the first eligible interactive-app composition with valid Blob configuration MUST create and locally persist one random UUID; missing/invalid configuration and excluded hosts MUST leave consent persisted without requesting or creating identity. Disable MUST retain an existing UUID without active-service identity request/use, and every later explicit opt-in and eligible app launch MUST reuse that same UUID for the app installation's lifetime. V1 MUST expose no install-ID Reset or rotation surface, require no shared-telemetry API change, and perform no host parsing of adapter-private storage or catalog state. The UUID MUST NOT appear in product properties, diagnostics, or evidence.
- **FR-024**: CLI, headless, and test hosts MUST never construct the Blob telemetry service or provision identity. Only the interactive app composition root MAY request/reuse identity and construct the service, and only after persisted consent plus valid configuration have both been established.
- **FR-025**: Under exact shared-telemetry `0.2.0`, legacy provider construction plus every Loki `track` and `flush` request MUST traverse one app-lifetime dedicated serial non-main executor. No app, Presentation, Application, or Infrastructure caller MAY retain or invoke the raw legacy provider directly; flush MUST execute after all earlier admitted requests, and only flushes adjacent in admission order MAY join the same active/queued flush. Because exact `0.2.0` calls `TelemetryQueue.enqueue` synchronously and completes its atomic persistence attempt or retained-memory fallback before `track` returns, that return MUST be the coordinator's barrier input before it starts a later underlying `flush`; the old `0.1.0` fire-and-forget return is explicitly insufficient. Tests beginning on `@MainActor` MUST prove construction and both operations are off-main, FIFO, and maximum-concurrency-one, cover both an adjacent joined flush and `flush → track B → flush` requiring a follow-up flush, and include an actual-`LokiTelemetryService`-shaped regression that records the real adapter's `track` completion before underlying `flush` entry. A synchronous fake alone MUST NOT establish the enqueue-barrier claim.
- **FR-026**: VoxPocket MUST NOT pass a `maxDiskBytes` override to the `0.2.0` legacy Loki or Blob initializer. It intentionally accepts the provider's 50 MiB persisted-data cap, whole-oldest-batch eviction, oversized-event rejection, durable dropped-event accounting, and capacity-aware rollback. Rollback MUST stop producers, finish pending paired eviction cleanup with the current capacity-aware reader after storage is writable, preserve the loss ledger and retained files, and never mix old/new writers; already evicted events are not recoverable.

### Key Entities

- **Product Event**: One trusted event name with only allowlisted finite numeric values or closed labels; never user content.
- **Blob Configuration**: The two build-expanded host values plus trusted app/build/version metadata and explicit enablement state.
- **Blob Store**: The dedicated local queue/catalog/ledger owned by one adapter instance; non-evicted files and ledger state are retained across retry or rollback.
- **Product Telemetry Consent**: A persisted `UserDefaults` boolean, default off, changed only through the “Send usage data” Settings control through a consent-only persistence interface, then consumed at the app composition boundary without provisioning identity itself.
- **Install Identity**: A random non-personal UUID absent until the first eligible interactive-app composition after explicit opt-in, retained but inactive across disable, and reused after every later opt-in and eligible launch for the app installation's lifetime.
- **Delivery Evidence**: Non-sensitive build number, workflow/run reference, tested revision, and blob name; excludes payload and credentials.

## Existing Behaviour

- VoxPocket pins shared-telemetry `v0.1.0` at full revision `5f4b4d97d7ad05adb849e0d8937c8745d9b6d15f` in VoxInfrastructure, VoxApplication, and VoxPresentation; that release has no public Blob adapter, and its legacy `track` returns after launching an unstructured enqueue task rather than after queue admission completes.
- `ServiceContainer.makeTelemetryService()` constructs the legacy Loki service from `LOKI_ENDPOINT`/`LOKI_TOKEN`; Release falls back to `NoopTelemetryService` without the endpoint. Existing use cases receive that raw service, so synchronous `track` can run on the caller (including `@MainActor`), and `endRecording()` launches its flush without one shared admission/flush executor.
- `VoxPocketLogging` independently mirrors allowlisted local logs to Loki and owns a separate persisted log queue.
- No host plist/build setting, TestFlight secret, Blob-only store, or Blob lifecycle exists. The current required app build does not prove Release plist expansion.
- No product-telemetry consent preference, “Send usage data” Settings control, or persisted install UUID exists.
- Existing telemetry records durations, counts, labels, and session IDs, but refinement and transcription failure paths also forward arbitrary localized/stringified errors. That conflicts with Constitution IV and the accepted privacy requirement.
- The release workflow is manual, checks out `main`, publishes macOS only, and injects App Store/signing secrets into Fastlane. iOS TestFlight remains disabled.

## Compatibility

- Loki endpoint/token selection, Noop fallback, local log mirroring, legacy safe event names/metrics, and session-end flush triggers remain in place; Blob is a second explicitly routed service. The approved compatibility exceptions are execution timing/thread and bounded retention: legacy provider calls move behind the shared serialized non-main coordinator, and `0.2.0` applies its accepted default capacity policy.
- The public Swift module/product remains `LokiKit`; the upgrade is additive. All consumer manifests, guards, authorities, and current projections move together with the coordinator adaptation in one atomic exact-`0.2.0`/off-main slice so neither `main` nor the reviewed candidate exposes the impossible old-`0.1.0` enqueue-barrier contract or mixed copies.
- Debug and credential-free Release builds remain usable with Blob disabled. iOS continues to compile/test but receives no newly authorized TestFlight release.
- Existing Settings pages and preferences remain; one default-off product-telemetry section is additive. CLI, headless, and test hosts retain zero Blob construction.
- No legacy queue is migrated or manually rewritten. The provider may evict whole oldest batches under the accepted 50 MiB default; already evicted events cannot be recovered. Rollback restores the prior dependency/config only after stopping all producers and completing any pending paired eviction cleanup with the capacity-aware reader; the loss ledger and retained files are preserved, old/new writers never overlap, and reverting code does not retract transmitted events.
- Source/project/CI/dependency paths covered by CODEOWNERS remain important and require Owner approval in their own single-goal PRs. No admin merge, force push, or protection bypass is authorized, and no review/check evidence is reused across PR heads.
- Real resource identifiers appear only in the Owner-command section of the PR body required by MY-1818, not in committed source, tests, fixtures, specs, or docs.

## Removed Behaviour

- **RB-001**: Remove arbitrary `error.localizedDescription` and stringified error/reason values from telemetry payloads; replace only with closed content-free categories where a failure distinction is needed. **Authority**: MY-1818 privacy requirement, FR-008/FR-009, and Constitution IV.
- **RB-002**: Do not route the existing legacy Loki event vocabulary into the Blob adapter; Blob accepts only the two product event types plus its SDK-owned heartbeat. **Authority**: MY-1818 “two base data types only,” FR-002/FR-005/FR-006.
- **RB-003**: Remove no Loki transport, safe metric, log sink, release guard, test, assertion, signing step, upload step, or platform restriction. VoxPocket performs no manual queue deletion; provider-owned eviction allowed by RB-005 is the only queue-retention exception. Any other removal requires a new decision.
- **RB-004**: Remove direct caller-thread invocation of the legacy provider. In the same atomic slice that selects exact `0.2.0`, legacy `track` and `flush` become serialized asynchronous submissions to one non-main app-lifetime coordinator, with the provider's synchronous enqueue return forming the barrier before a later flush. **Authority**: 2026-10-16 Lead decision `loki02v1` / `atomic-0.2.0-offmain-plan`, Constitution III, FR-025, and implementation-review verdicts `01a142ea-d4bb-77d9-8663-fcea48467100` / `01a142f8-f0f7-7c99-8435-75c6131b5631`.
- **RB-005**: Remove any assumption of unbounded legacy/Blob persisted retention. With no consumer override, the provider's 50 MiB default may reject an oversized event or evict whole oldest batches and records durable loss; already evicted events are unrecoverable. **Authority**: 2026-10-16 Lead decision `A-keep-0.2.0-offmain-accept-defaults`, FR-026, pinned provider `ai/MIGRATION.md`.

## Scope Boundaries

### In scope

- Immutable shared-telemetry adoption in existing consumers and its repository dependency guard, including the app-shell legacy Loki coordinator adaptation required to keep synchronous provider I/O off `@MainActor`.
- A separate Blob-only app service, typed two-event product vocabulary, privacy policy, bounded app-lifetime retention, dedicated store, and flush wiring.
